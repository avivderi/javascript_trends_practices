<h1 dir="rtl">מעבדת רובוטיקה תיכונית — תלמידים ומפגשי מעבדה</h1>

<h2 dir="rtl">רקע</h2>

<div dir="rtl">

בית ספר תיכון מפעיל מעבדת רובוטיקה. שני צרכים שונים לגמרי במעבדה:

1. **ניהול תלמידים** — המערכת מנהלת את תלמידי המעבדה. לכל תלמיד נשמרים
   פרטיו האישיים וכן רשימת מזהי מפגשי המעבדה אליהם הוא רשום. הרשימה
   מתעדכנת לאורך השנה כאשר תלמיד נרשם למפגשים חדשים או מסיים השתתפות
   במפגשים קיימים.

2. **מפגשי מעבדה** — כל מפגש מעבדה (יום+שעה מסוימים) מוגדר מראש עם
   **קיבולת מקסימלית** של מקומות. תלמידים נרשמים למפגש, וההרשמה **אסור**
   שתעבור את הקיבולת.

**לא נאמר לכם איזה DB להשתמש בכל יישות — אבל הפעם הסיפור בנוי כך שיש לזה
תשובה "נכונה" מבחינה עניינית, וחלק מהתרגיל הוא לזהות אותה ולנמק אותה נכון
ב-README:**

- יישות שבה נשמר מידע של אובייקט יחיד, הכולל גם רשימה של מזהים
  הקשורים אליו, כאשר אין צורך אמיתי בטרנזקציות חוצות-רשומות —
  עשויה לרמז על DB מסמכים.

- יישות שבה יש **אילוץ קיבולת קשיח שצריך לשמור עליו בצורה אטומית מול
  בקשות מקבילות** — מרמזת על DB יחסי עם טרנזקציות/אילוצים (constraints)
  ברמת בסיס הנתונים.

התרגיל לא "אוסר" עליכם לבחור אחרת — אבל אם תבחרו אחרת, תצטרכו להסביר
ב-README איך התמודדתם עם החיסרון (למשל: איך שומרים על אטומיות בקיבולת
בלי DB יחסי, או כיצד בחרתם לייצג את הנתונים ב-DB יחסי/מסמכים).

</div>

<h2 dir="rtl">יישות 1: תלמידים (Users)</h2>

<div dir="rtl">

**רשומת תלמיד:**

</div>

```json
{
  id: string,
  firstName: string,
  lastName: string,
  className: string,
  labSessionsIds: string[]
}
```

<div dir="rtl">

- `labSessionsIds` מכיל את מזהי מפגשי המעבדה שאליהם התלמיד רשום.
- כל מזהה ברשימה מייצג את ה-Primary Key של מפגש המעבדה.
- אין לשמור בתוך רשומה זו מידע נוסף על המפגש מעבר למזהה שלו.

</div>

קלט:

</div>

- בקשה שהייתה גורמת לחריגה תידחה עם קוד שגיאה מתאים (`400` או `409`).

<h2 dir="rtl">יישות 1: תלמידים — מה לבדוק</h2>

<div dir="rtl">

### **`POST /users`**

- יצירה תקינה של תלמיד חדש.
- יצירה עם אחד או יותר מהשדות החובה חסרים → קוד שגיאה מתאים.
- וידוא שהמשתמש נוצר עם `labSessionsIds` כמערך ריק.
- ניסיון ליצור מספר תלמידים עם אותם נתונים (אם קיימת מדיניות בנושא) — יש לבדוק שההתנהגות תואמת למה שתועד ב-README.

---

### **`GET /users/:userId`**

- תלמיד קיים → מוחזרים כל פרטיו.
- תלמיד הרשום למספר מפגשים → מוחזר מערך `labSessionsIds` עם כל המזהים.
- תלמיד שאינו רשום לאף מפגש → מוחזר מערך ריק.
- תלמיד שאינו קיים → `404`.
- וידוא שנתוני תלמיד אחד אינם "דולפים" לתלמיד אחר.

</div>

---

<h2 dir="rtl">יישות 2: מפגשי מעבדה — מה לבדוק</h2>

<div dir="rtl">

### **`GET /sessions/:sessionId`**

- מפגש קיים ללא נרשמים →
  `registeredCount: 0`,
  `remainingSpots` שווה ל-`capacity`.

- לאחר מספר הרשמות מוצלחות →
  `registeredCount` ו-`remainingSpots`
  מתעדכנים בהתאם.

- מפגש שאינו קיים →
  `404`.

---

### **`POST /sessions/:sessionId/register`**

- הרשמה בודדת למפגש עם מקום פנוי →
  `201` +
  `remainingSpots` נכון.

- ניסיון לרשום תלמיד שאינו קיים →
  קוד שגיאה מתאים.

- הרשמה למפגש מלא →
  נדחית עם קוד שגיאה מתאים
  ו-`remainingSpots: 0`.

- הרשמה כפולה של אותו תלמיד לאותו מפגש →
  יש לבדוק שההתנהגות תואמת למה שתועד ב-README
  (שגיאה / התעלמות / `200` ללא שינוי).

- בכל מקרה, הרשמה כפולה **לא** תגרום לספירה כפולה של אותו תלמיד
  ב-`registeredCount`.

- לאחר הרשמה מוצלחת יש לוודא שמזהה המפגש נוסף
  ל-`labSessionsIds` של אותו תלמיד.

- אם ההרשמה נדחתה (לדוגמה בגלל חריגה מהקיבולת),
  אין לעדכן את נתוני התלמיד.

<h1 dir="rtl">בונוסים (אינם חובה)</h1>

<div dir="rtl">

הסעיפים הבאים הם בונוס בלבד. ניתן לממש אחד או יותר מהם לפי בחירתכם.

</div>

### בונוס 1 – יצירת מפגש מעבדה

ממשו אנדפוינט:

```
POST /sessions
```

קלט:

```json
{
  "topic": "Arduino Basics",
  "dateTime": "2026-08-10T09:00:00Z",
  "capacity": 20
}
```

פלט:

```
201 Created
```

עם פרטי המפגש שנוצר.

יש לוודא:

- `capacity` גדול מ־0.
- `dateTime` בפורמט תקין.
- מזהה המפגש נוצר אוטומטית.

---

### בונוס 2 – ביטול הרשמה למפגש

ממשו אנדפוינט:

```
DELETE /sessions/:sessionId/register/:studentId
```

לוגיקה:

- להסיר את התלמיד מהמפגש.
- להסיר את מזהה המפגש מתוך `labSessionsIds` של התלמיד.
- אם התלמיד אינו רשום למפגש, יש להחזיר קוד שגיאה מתאים.

---

### בונוס 3 – חיפוש מפגשים

ממשו אנדפוינט:

```
GET /sessions
```

שיתמוך בפרמטרי Query כגון:

```
GET /sessions?topic=arduino
GET /sessions?date=2026-08-10
GET /sessions?capacity=10
```

---

### בונוס 4 – מניעת התנגשות שעות

בעת הרשמה למפגש חדש, אין לאפשר לתלמיד להירשם לשני מפגשים המתקיימים באותו תאריך ושעה.

---

### בונוס 5 – הצגת פרטי המפגשים של תלמיד

ממשו אנדפוינט:

```
GET /users/:userId/sessions
```

במקום להחזיר רק את `labSessionsIds`, יש להחזיר את פרטי כל המפגשים אליהם התלמיד רשום.

> ניתן לממש זאת בכל דרך שתבחרו, כל עוד הארכיטקטורה והבחירות מתועדות ב־README.

---

### בונוס 6 – ולידציה מלאה

השתמשו בספריית ולידציה (לדוגמה Joi, Zod או Express Validator) עבור כל האנדפוינטים במערכת.

---

### בונוס 7 – תיעוד API

הוסיפו תיעוד API באמצעות Swagger / OpenAPI כך שניתן יהיה לבדוק את כל האנדפוינטים דרך הדפדפן.
